# Shurufa 迭代方向（更新思路）

本文来自对搜狗输入法官方升级日志（PC 版与手机版在 2024-2026 年的迭代轨迹）的整理，并结合 Shurufa 目前的能力现状（Windows TSF + librime 雾凇拼音 + Android 输入法 + 跨设备剪贴板）提出一份可作为路线图参照的迭代方向。

生成时间：2026-08-08

---

## 摘要

搜狗近 2-3 年的升级集中在四个维度：

1. **候选与打字策略**：候选条/翻页/光标/首屏位置；多少候选、如何对齐习惯键盘位置。
2. **AI 与写作辅助**：AI 帮写、续写、润色、纠错、语意翻译、语音模型的持续升级。
3. **跨设备与多模态**：剪贴板跨设备复制粘贴（文本/图片/文件）、手机/平板/电脑的流动性。
4. **外观与个性化**：皮肤、主题、键盘布局、右上角指示灯、自定义工具栏；让专业与轻量用户都能找到自己的生活风格。

Shurufa 若在这四个维度分层推进，则可以把当前 Rime/librime + 剪贴板同步的骨架，逐步演化为更像搜狗/讯飞那样的“输入助手”体验，同时保持开源、可自建、无后台广告数据收集的差异化定位。

---

## 一、打字体验：候选词、翻页与光标（最高优先级）

### 1.1 候选页容量与层级化
- 参考：搜狗手机版“候选条精简”“多行候选/翻页布局切换”，搜 Dog PC 版“候选条界面重构”“下方翻页/更多候选用上下翻页”。
- 方向：
  - 在现有 `page_size=5` 的基础上，逐步加入“候选上下文”概念：当前行展示 + 下方备选的候选项聚类（同音同形/词语联想/表情/翻译候选）。
  - 允许长按候选条某个条目弹出菜单（复制、删除、加入自定义词频模式）。
  - 候选分页里引入“上次使用的候选队列”概念（不只按词频绝对排序，也考虑最近输入上下文）。

### 1.2 光标插入与位置编辑
- 参考：搜狗版对“点击拼音中间插入字符”这类长期的老bug从没有明确日志，但该功能外网存在已久；它偏底层，需要拼音拆解、引擎光标在 raw input 上的精准映射。
- 方向：
  - 当前已新增 `set_caret_pos` 原生精准插入；后续可扩展信息视图，在 preedit 上渲染“拼音分词视图”（如 `ni hao` 拆成 `ni / hao`），并提供候选内导航（Ctrl+左右/Tab/Shift+Tab）定位到某一音节上。
  - 引入“光标上下文候选”概念：当 preedit 相同但上下文不同的场景（如聊天、邮件、代码）中点亮不同的候选分级与展示策略。

### 1.3 切换与信号指示
- 参考：搜狗“Shift 切换中英文”“中英全角符号；大写锁提示；CapsLock 指示灯”。
- 方向：
  - 补充 `nativeIsAscii`、`nativeToggleAscii` 到 UI 反馈，候选栏对应显示“当前中/英文”。
  - 长按 Shift 进入大写模式（类似手机双击 Shift）；在键盘上对应加一个 Shift 状态指示。
  - Windows 平台要解决中英文混合输入时的流畅度（如快速连续中英文切换到的空格与时序控制），避免候选条残留旧切换状态。

## 二、AI 与写作辅助（选择性推进）

### 2.1 写作风格工具（非侵入式）
- 参考：搜狗的“AI帮写”“高情商回复”“灵感语录”“AI划词翻译”。
- 方向：
  - 这部分能力不建议直接取代当前 Rime 候选；建议做成**辅助视图**（如 `Ctrl+Shift+W` / 手势呼出面板 / 特定场景自动弹出）。
  - 实现路径：先用开源/本地模型（如 Ollama / llama.cpp / 用户自选 OpenAI API）接入，让用户自选模型是本地或远端。
  - 在 Shurufa 上记录词典：把高频写作短语（成语、新闻俚语、机构名）作为可选自定义数据包导入，不干扰词库本身的稳定性。

### 2.2 语音输入与语音纠错
- 参考：搜狗手机版持续强化语音（MV、网格、识别更准；离线环境可用）。
- 方向：
  - 当前的 Android 端语音模块和剪贴板服务可以合并：语音输入的临时结果直接进剪贴板，作为一个“语音哥白尼”功能（快速语音+粘贴到任意框，类似飞书的复制模式）。
  - 为用户提供“常用口语转为规范书面语”的切换（让语音结果不仅仅是原样转写，还可选“规范化”修饰）。

### 2.3 拼音之外的输入方式
- 参考：搜狗拼音支持双拼、五笔（企业版/开源兼容）、辅助码。
- 方向：
  - 如果现有 Rime 方案支持，则增强对双拼/五笔等输入法入口的支持，使其在 Shurufa 框架下可以平滑切换，不是替代而是补充。
  - 在输入语言与引擎的开放性上，保持与 Windows、macOS 原生输入法的兼容性。

## 三、跨设备同步与剪贴板（强化现有优势）

### 3.1 剪贴板层的稳定性
- 参考：搜狗“跨设备复制粘贴”（文本/图片）、变态、一键两端切换发送等能力。
- 方向：
  - 现有 `ClipboardSyncService` 已有同步框架，下一步强化：
    - 失败重试 / 离线缓存 / 重新注册时机（如设备恢复 Wi-Fi 时）。
    - 同步超时、冲突策略（不同设备同时复制不同类内容时可指明使用哪一条）。
  - 引入更明确的“发送来源标签”（当前仅为“本机/同步·Peer”），让用户知道内容来自哪台设备，避免错误操作。

### 3.2 跨设备界面
- 参考：搜狗“Android 工具栏自定义”“剪贴板排版多样化”“历史记录 UI 聚合”。
- 方向：
  - 当前 Android 端的历史面板/预览键盘已有基础；可以增加“历史筛选（按来源设备/消息类型/收藏）”“跨设备搜索”。
  - Windows 控制中心逐步整合剪贴板历史管理（现有 UI 已有）与多设备同步（配合现有 relay），将设置和日常操作模块化。

### 3.3 同步与隐私
- 参考：搜狗支持跨设备但是部分广告/数据隐私正在凸显。
- 方向：
  - 保持 Shurufa 的独立自建定位：支持私有导航服务器、自托管、可配置的策略（不开启数据收集），把“同步”作为开源卖点。

---

## 四、外观、皮肤与个性化（中等优先级但提升感知）

### 4.1 皮肤与主题
- 参考：搜狗皮肤标识、自定义键盘布局、换面板/换颜色的机制，长期在桌面和移动端存在。
- 方向：
  - 当前 `schemas/shurufa-skin.json` 是跨端皮肤入口，可以扩展为“主题包”：支持下载、商店机制（用户可自行上传/复用），让用户可基于 JSON 统一调整。
  - Android 侧可以增加“布局微调”（如候选框高度/行距/字体大小/亮暗色模式），把键盘的 adaptiveness（按钮响应/轻触感）作为可选设置。

### 4.2 工具栏/快捷入口
- 参考：搜狗手机版工具栏扩容（30 个 icon + 固定工具栏 + 最近使用）、设置面板清晰化。
- 方向：
  - 将当前“剪贴板”按钮为代表的工具栏做成更灵活的扩展点：可以把表情、回复片段、AI 工具、翻译、换皮肤都挂接到工具栏上。
  - Windows 控制中心把“候选项修正（符合用户码表习惯）”“输入法切换模式”“多设备管理”等工具整合到一个视觉层级明确的设置面板中，避免深层页面。

---

## 五、工程架构与性能（贯穿所有迭代）

### 5.1 引擎与 UI 分层
- 保持 librime 引擎与 UI 层级分离（当前 Windows 用 TSF 是合理的）；Android 侧持续优化输入延迟（JNI 引擎单例、异步预热、增量加载表）。

### 5.2 测试与验收机制
- 当前工程已覆盖大量 Rust/JNI 单元测试；后续可以：
  - 在 Windows 持续做 UI 端 E2E 验证工具（Tauri App 组合测试运行）。
  - 在 Android 上增强集成测试（JNI 集成 + 输入法生命周期模拟式验收），避免键盘打开态、面板切换、跨设备消息等场景回归。

### 5.3 兼容性与更新通道
- 保持 install/upgrade 流程的兼容性；在 NSIS / Tauri 安装器上进一步明确“回退策略”（失败时回退到上一个版本或默认布局），减少更新损坏对用户的影响。

---

## 结语

搜狗的迭代经验告诉我们：输入法的关键不是“表面花哨”，而是把打字、候选、屏幕、跨设备的核心体验做到“顺手”，再加上逐渐增强的辅助功能（AI、语音、个性化），并且在所有设备上保持一致的视觉反馈与操作体验。Shurufa 一步步走，最后会形成一个深度定制化但不过度膨胀的开源输入法体验。

此文档会持续更新，根据工程演进和用户反馈，不断调整优先级与实施细节。

**Windows 设置中心（`platforms/windows-settings`）**

### D2. 第二批追加交付（2026-08-08 深夜批次）

承接 §一/§二/§三/§四遗留：**协议协商**、**AI 帮写** 与 **候选副标** 全部落地。

**core/sync（剪贴板 wire protocol v2，`core/sync`）**
- `Message::Hello` 新增 `features: Vec<String>` 与 `protocol_version: u32`（serde default 1 → 老版本端仍能反解）。
- `Message::ClipText/ClipImage/ClipFile` 新增 `msg_id: Option<String>` + `origin_device_fp: Option<String>`，全部 `#[serde(default)]`。
- 新常量：`FEATURE_MSG_ID_V1`、`FEATURE_LWW_V1`、`PROTOCOL_VERSION = 2`；`peer_supports(features, name)` 判定对端能力。
- `Shared` 新增 `recent_out: Mutex<Vec<(String, i64)>>`（环形 64 槽），记录本端近期发出的 (msg_id, sent_at_ms)。
- `Outbound::Text` 携带 `msg_id`（32 hex chars）+ `sent_at_ms`；`duplex` 收侧运行两级回声剔除：
  - ① `origin_device_fp == 本端指纹` → 直接 skip（强匹配）
  - ② `(msg_id, sent_at_ms ± 5s)` 与 `recent_out` 匹配 → skip（弱匹配，覆盖旧版本端 echo）
- 只有对端 hello 宣告 `msg-id-v1` 时才在 wire 上写 msg_id / origin_device_fp；旧端仍按 v1 协议通讯。

**Windows 桌面（`platforms/windows-host`）**
- 新增 `ai_panel.rs`：Ctrl+Shift+W 呼出 AI 帮写面板（独立窗口类 `ShurufaAiPanel`，与候选人区分）。
  - 状态机：Editing → Pending → Preview / Failed / Misconfigured。
  - Pending 阶段用 `Instant::now` 显示 "思考中…（X s）"。
  - Preview 用 `DT_WORDBREAK` 多行预览 220 字；Esc 关闭，回车粘贴草稿到原前台（先 `set_clipboard_text` + `SetForegroundWindow` 回前台 + `SendInput` 发 Ctrl+V，先抬 Shift 避免变 Ctrl+Shift+V）。
  - Failed 显示 R 键回编辑态；Misconfigured 直接提示用户在系统属性里加 `AGNES_API_KEY`（**key 不入日志/配置/剪贴板，只在请求时读取**）。
  - HTTP 客户端：ureq 2.12，`POST https://apihub.agnes-ai.com/v1/chat/completions`，模型 `agnes-2.5-flash`，`stream=false`，45s 超时；worker 线程跑 + `PostMessageW(WM_AI_DONE)` 回 UI 线程，`Box<(String, Result<String, String>)>` 经 LPARAM 转移所有权。
  - 内置系统提示约束输出 300 字以内可粘贴中文段落。
- `listener.rs` 在消息循环里同时分发 `HOTKEY_ID=1`（历史）和 `HOTKEY_ID=2`（AI）；`main.rs` `mod ai_panel;`。

**Android（`platforms/android/app`）**
- 功能行新增第三个 chip `🪄 AI 帮写`，独立面板 `aiPanel`（不与 historyPanel 共用），布局：标题栏（标题+✕） / `EditText`（IME_ACTION_SEND） / 状态行 / 草稿预览（可选中复制，包 ScrollView） / 底部按钮组（粘贴 + 重试）。
- `readAiApiKey()` 用反射从 `BuildConfig.AGNES_API_KEY` 读；gradle 端 `buildConfigField` 把 `providers.gradleProperty("AGNES_API_KEY").orElse(providers.environmentVariable("AGNES_API_KEY"))` 注入，绝不下落 gradle.properties 入仓。
- `callAgnesChat`：`HttpURLConnection` POST，15s connect / 45s read，请求体直接用 `org.json.JSONObject` 构造（消息结构 = system prompt + user prompt，与 PC 同）。错误区分 HTTP 状态码与网络异常。
- `ioExecutor.execute` 跑网络，`mainHandler.post` 回主线程更新 UI；成功后 `commitAiDraft()` 走 `ic.finishComposingText() → commitText(draft, 1)`，关闭面板回到键盘。
- `onFinishInput` 同时复位 aiPanel（可见性 + 清空状态/草稿），避免下次打开看到上一次失败态。

**Windows TSF（`platforms/windows/src/candidate_window.rs`）**
- `Item` 新增 `comment` 字段（引擎候选附注，雾凇拼音会给 emoji/近义词/词条类别等）。
- `show()` 测量阶段新增 `comment_w`（用 sub_font 实测），叠加进 `text_w` 占住后续槽位避免重叠。
- `paint()` 在主文本右侧 `+2px` 用小号灰字渲染 comment，单行不换行；不与 text 相同的 comment 自动隐藏为 `""`。

### H.2 `metrics.scrollbar` + `metrics.icon`（候选窗 schema 扩展）

- `metrics.scrollbar: bool`（默认 true）：候选窗右缘 4px（96 DPI 基准，DPI 缩放）轨道 + thumb；仅当开关开 `且` 引擎透传分页上下文非单页（`page_no/is_last_page → total_pages > 1`）才画。
- 渲染色：轨道 = `candidate.background` 调深 29/32（对明度 <0x20 的近黑底反向 +24 提亮，避免暗皮轨道变死黑）；thumb = `highlight_background`。
- thumb 几何：高度 = 单 item 槽宽（clamp [20, span]）；垂直位置按 `page_no / max(total-1, 1)` 在轨道内线性移动。纯视觉，不支持拖动。
- 双后端：GDI `FillRect` 在 `paint()` 背景之后；D2D `FillRectangle` 紧跟候选行后（thumb 圆角暂不求，直角与槽位一致）。两条路径共用 `skin::scrollbar_geo()` / `scrollbar_colors()` 纯计算（schema 层导出，host/TSF 共享同一份代码）。
- `scrollbar=false`（或单页）：窗口宽度计算中 `sb_w=0`，无任何布局偏移；命中测试上轨道区间按下/上半区发 PgUp/PgDn（与现有滚轮翻页一致），点击候选范围外（如 preedit 行空隙）不产生任何按键。
- `metrics.icon: Option<String>`（预留）：以 `IconSlot`（64 字节 UTF-8 Copy 槽）携带，保 `Metrics`/`Skin`/`Skin::current()` 全链 `Copy`；本版本不渲染，仅一次性 `debug_log("skin: metrics.icon slot reserved, not yet rendered")`。后续把 per-candidate 图标查表（Rime 候选注释/类型到 emoji/asset 的映射）接到这个槽位，无需再改 JSON 解析。

## 附录 I：文件同步 v3（2026-08-11 落地）

本附录记录「跨设备文件同步（Offer/Accept/Chunk/Done/Ack）」本次落地的实现决定与协议面，便于回查。

### 协议面（core/sync/src/protocol.rs）

- `PROTOCOL_VERSION = 3`；本端通过 `local_features()` 宣告 `"file-v1"`；
- 七个新变体以 `#[serde(tag = "type", rename_all = "snake_case")]` 入管道，所有字段均带 `#[serde(default)]`，向下兼容 v2（v2 端不写新字段、v3 端读到缺省字段用默认值）：
  - `FileOffer { msg_id, name, size, mime, sha256, chunk_bytes }`
  - `FileAccept { msg_id }`
  - `FileDecline { msg_id, reason }`
  - `FileChunk { msg_id, offset, data /* base64 */, last }`
  - `FileDone { msg_id, sha256 }`（`sha256` 字段冗余于 Offer，便于 Done 单独校验）
  - `FileAck { msg_id, received_bytes, ok, error }`
  - `FileProgress { msg_id, received_bytes }`
- 帧上限沿用 16 MB；chunk_bytes 固定 64 KiB（base64 编码后 ~87 KB 一帧）；1 MB 文件 = 16 块。

### 生命周期（Offer → Accept → Chunk* → Done → Ack）

- 发送端（`SyncService::send_file_path`）：
  - 读盘 + sha256 + 分块在 `tokio::task::spawn_blocking` 中做（≤64MB 限制）；
  - 广播 `FileOffer` → 30s 等待 `FileAccept`（超时由内部 watchdog 将状态切 `Failed("对方未响应")` 并 emit `Incoming::FileTransferDone`）→ 按序推 Chunk（每 4 块让出调度，~2MB/s 上限） → `FileDone` 收尾；
  - 收到接收端 `FileProgress` 时刷新 `Streaming{sent_bytes}` 并 emit `Incoming::FileProgress` 供 UI 渲染；
  - 收到 `FileAck` 时按 `ok/error` 切终态（`Acked` 或 `Failed`）并 emit `Incoming::FileTransferDone`；
  - 状态机在 `Shared::transfers: Mutex<HashMap<String, FileSendState>>` 中存（`OfferSent/Streaming/StreamDone/Acked/Declined/Failed`），供测试 / UI 轮询。
- 接收端（duplex 内分发）：
  - `size > 64MB` → 立即 `FileDecline("too_large")`；
  - 否则 emit `Incoming::FileOffer` 通知宿主，并按 `file_confirm` 回调返回值决定；无回调时按 `size < 5MB && mime ∈ {image/*, text/*, application/pdf, application/zip}` 白名单自动接受；
  - 接受时创建 `<landing>/<msg_id>.part`（空文件 touch），发 `FileAccept`；
  - 收 `FileChunk`：按 offset 顺序 Append 到 `.part`；乱序 → `FileDecline("chunk_out_of_order")`；每 16 块或到位时回 `FileProgress`；
  - 收 `FileDone`：比对 sha256，一致 → 原子重命名为最终文件名（重名加 ` (2)`/` (3)` 后缀），发 `FileAck{ok:true,received_bytes:size}` 并 emit `Incoming::FileTransferDone{ok:true}`；不一致 → 删 `.part` 并发 `FileAck{ok:false,error:"sha256_mismatch"}`。
- 大小约束：单文件 64 MB（`MAX_FILE_BYTES`），两端一致；预期外尺寸在 Offer 处立即拒。

### 落盘目录

- 默认 `<USERPROFILE|HOME>/Downloads/shurufa/`（Windows / Linux / macOS 一致命名，Android 用 `filesDir/sync/received/`，由 `file_recv_dir_override` 持有最终路径）；
- 测试可使用 `SyncService::set_file_recv_dir_override` 注入替身目录；`file_sync.rs` 用此机制在 tempdir 下断言结果；
- 落地命名冲突自动追加 ` (2)`/` (3)` 等。

## 附录 M：双端文件 Offer 审批（2026-08-11 启动）

C3 把 C2 的「自动 < FILE_AUTO_ACCEPT_MAX + MIME 白名单 / 自动拒绝」接收侧策略
升级为可由 UI 覆盖：sync-core 暴露决策回调与 transfer_id，Android 端用系统通知
（接受 / 拒绝 Action）回送用户选择；通知被禁用或 Kotlin 未挂回调时回退到既有
auto 路径。

### sync-core 接入面

- **类型**：`FileOfferPrompt { transfer_id: u64, peer_fp: String, from_name, name, size, mime }`，
  `FileConfirmFn = Arc<dyn Fn(FileOfferPrompt) -> bool + Send + Sync>`。
  `transfer_id` 由 `AtomicU64` 从 1 起自增（仅进程内有效，用于把「通知按钮点击」
  回指到本条 Offer）；`peer_fp` 为发送侧 SHA-256 证书指纹，UI 可截前 8 位展示。
- **生命周期**：duplex 在 FileOffer 到达时把 `prompt` 入 `Shared.pending_offers`
  表（`Mutex<HashMap<u64, FileOfferPrompt>>`），随后 `tokio::task::spawn_blocking`
  执行宿主回调（允许阻塞等用户点击），回调返回后落终态并出表。
- **公开方法**：
  - `SyncService::set_file_confirm_handler(Option<FileConfirmFn>)` — Some 时由宿主决策，
    None 时回到自动策略；
  - `SyncService::file_pending_offers() -> Vec<(u64, FileOfferPrompt)>` — 当前正在等用户
    决策的 Offer 列表，宿主启动时 / 通知恢复时可遍历补齐 UI 状态。

### Android 链路

- **JNI（platforms/android/rimejni/src/sync_jni.rs）**：
  - `nativeSetFileConfirmCallback(cb)` — 把 Kotlin 的 `IFileConfirmCallback` 包装为
    GlobalRef 并注入 sync-core；回调在 Rust `spawn_blocking` worker 里同步调用
    `onOffer(name, sizeBytes, mime, peerFp)`，Kotlin 立即返回 true（=「我会稍后回送」），
    Rust 侧随后在 `std::sync::mpsc` 上 `recv_timeout(25s)` 阻塞等 `nativeConfirmOffer`。
    Kotlin 回调返回 false 或 JNI 异常 / attach 失败 → 立即拒绝且不阻塞。
  - `nativeLatestPendingOfferId(): Long` — Kotlin 在 `onOffer` 里反查 transfer_id。
  - `nativeConfirmOffer(transferId: Long, accept: Boolean)` — 通知按钮的广播接收器侧
    把布尔结果送回对应回调，解除阻塞。
- **Kotlin（SyncBridge.kt）**：
  - `IFileConfirmCallback.onOffer(...)` 实现里用 transfer_id 组装 PendingIntent，
    弹 `NotificationCompat` 通知（CHANNEL `file_receive`，IMPORTANCE_HIGH、
    action=接受 / 拒绝、smallIcon=`android.R.drawable.stat_sys_download`）。
  - 通知按钮的 BroadcastReceiver 通过 `Context.registerReceiver` 挂在
    `SyncBridge.ensureStarted` 内完成注册（API 33+ 用 `Context.RECEIVER_NOT_EXPORTED`），
    AndroidManifest 无需声明静态 receiver。
  - 「接受 / 拒绝」触发 `nativeConfirmOffer(...)` 并 `NotificationManagerCompat.cancel(...)` 收尾。
- **失败兜底**：`POST_NOTIFICATIONS` 被拒、JNI attach 失败、回调抛异常均按拒绝处理。
  若 Kotlin 未挂回调（`nativeSetFileConfirmCallback(null)` 或从未设置），sync-core
  回到既有 auto 策略（< 5MB + image/text/pdf/zip 白名单 → 自动接受；否则自动拒绝，
  理由字符串 `user_declined` / `too_large` / `io_error`）。

### 与 C2 auto 策略的关系

`set_file_confirm_handler(Some(...))` 之后 decision 完全交给 UI，`FILE_AUTO_ACCEPT_MAX`
与 MIME 白名单不再生效；清空或传 `None` 立刻回退。本端 25s 决策超时与发送端 30s
OfferSent 看门狗之间留 5s 余量，确保用户即使长时间未点击通知，发送侧也能在合理
时限内收到 `user_declined` 而非看门狗 `timeout`。

## 附录 N：候选窗 DComp GPU 直渲（2026-08-11 启动）

### 为什么要 DComp（而不是停在 D2D 1.1 + HWND render target）
- **vsync 与帧同步由 DWM 托管**：flip-model swapchain `Present(1, 0)` 交给合成器节拍，不再像 `ID2D1HwndRenderTarget` 那样在 `EndDraw` 时通过 GDI 兼容路径即时 present——窗口可见期间几乎不再有撕裂/抖帧的空间。
- **GPU 合成而非 GPU 光栅化 + GDI 直通**：候选人形圆角、阴影、透明度全部作为 premultiplied-alpha 纹理直接进 DWM 树（`IDCompositionTarget` + `IDCompositionVisual`），省掉一次 GDI redirection surface 的往返。
- **行级 visual 槽位已预留**：当前每帧重画一张纹理；后续做"翻页/选位变化仅 `SetOffsetX2/Y2`"即可零纹理重建（`IDCompositionAnimation` 挂 `OffsetX/Y2` 上，不重建 swapchain 位图）。这是 D2D 路径给不了的——hwnd target 的整套资源随尺寸/DPI 一变就得重画。

### 瀑布链：DComp → D2D → GDI
`backend_kind()` 在 thread-local 懒解析一次：
1. `probe_dcomp_available()`（D3D11 设备 + IDXGIFactory2 + DCompositionCreateDevice 全通）→ `BackendKind::DComp`
2. `candidate_window_d2d::is_enabled()`（既有 DXGI/D2D1 factory）→ `BackendKind::D2D`
3. 兜底 `BackendKind::Gdi`——纯软件路径，恒可用，绝不 panic

帧级失败（`EndDraw` RECREATE / `Present` DEVICE_REMOVED / 任何 HRESULT）在当前帧返回 false，**本帧立刻落下一级重画**，画面不丢；下一帧由各自的 `notify_resize` + 惰性重建吸收，不永久钉死在低档位。

### 圆角与 alpha 的工程要点
- 透明底 `Clear(D2D1_COLOR_F{a:0})` 起笔，圆角用 `FillRoundedRectangle` 画进 premultiplied-alpha swapchain 纹理；抗锯齿边缘天然预乘，合成时视觉零瑕疵，不需要 `WS_EX_LAYERED`。
- 窗口带 `WS_EX_NOREDIRECTIONBITMAP`（candidate_window.rs 的 `CreateWindowExW`），内容不经 GDI 中转；DComp 绑窗口时仍走同一 HWND。
- swapchain：`BufferCount=2` + `FLIP_SEQUENTIAL` + `AlphaMode=PREMULTIPLIED` + `Scaling=STRETCH`，`Format=B8G8R8A8_UNORM`；DPI 变化时 swapchain 整链重建（与 D2D 后端的 `notify_resize` 同一拍）。

### Feature gating
当前**不**加 cfg gate：windows crate 0.62 已暴露 `Win32_Graphics_DirectComposition` + `Win32_Graphics_D3D11` + `Win32_Graphics_Dxgi`，`Cargo.toml` 启用这三个 feature 即可，**未引入任何新 crate 依赖**。若未来发现某 API 在锁定版本仍缺，回退方案是 `#[cfg(feature = "dcomp")]` + Cargo feature `dcomp`，但当前 wave 直接无条件编译。
