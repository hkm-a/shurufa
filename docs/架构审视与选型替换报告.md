# Shurufa 架构审视与选型替换报告

审查日期：2026-08-21 · 审查基线：`d2a8b5d` · 审查范围：全仓 10 个子系统

---

## 0. 摘要

**一句话结论：骨架选型是对的，填充物系统性自研；项目自称最高优先级的「标准化 + 生态复用」，兑现率约四成。**

真正的风险不在代码质量——手抄 98 项 librime FFI 至今零漂移，说明执行力没问题——而在于**三个本该拦住自研的机制全部失效**，导致自研面还在加速扩张，而它恰好又是测试覆盖不到的那部分。

| 维度 | 实测 |
|---|---|
| 代码量 | Rust 37,433 行（12 crate）+ Kotlin 11,087 行 + JS 12,700 行（其中 **9,116 行是 vendored 第三方**） |
| 仓库年龄 | **24 天**（2026-07-29 → 08-21），213 次提交 |
| 提交结构 | 48 `feat` : 12 `fix` : **1 `refactor`** |
| 全周期删增比 | 59,600 增 / 11,079 删 = **0.186**——写下的东西基本没进过维护期 |
| CI 状态 | main 分支近 **14 次运行 14 次红**，唯一绿的是 v1.8.0 的 Release 作业 |
| 可替换的自研 | 约 **12,000 行**有成熟替代品，其中多数替代品**已在 `Cargo.lock` 里** |

**三个失效的拦截机制：**

1. **CI 全红** —— 仓库未钉 Rust 工具链（无 `rust-toolchain.toml`），本地 clippy 1.97 是绿的，CI 的浮动 `stable` 带来新 lint 后转红并一直红着。红了的 CI 等于没有 CI，`README.md:98` 的「clippy/fmt 零告警、约 240 项测试全绿」自 v1.0.0 起就不成立。
2. **架构文档失真** —— `docs/架构说明.md` 冻结在 2026-08-08，其承诺的 Compose 键盘、WiX 安装器、uniffi 绑定、QUIC 传输**四项全部与实现不符**，且没有一条负向决策记录（唯一的例外是 QUIC→TCP 那段，写得很好，应作为范式）。
3. **单一事实源破裂** —— `version.json` = 1.8.0/40，`README` 徽章 = v0.8.0，`README` 正文 = v1.7.0/39；`set-version.ps1 -Check` 只校验 4 处白名单，README 与 Android 都不在内。

**最该先做的五件事**（详见 §6）：

| # | 动作 | 代价 | 为什么是它 |
|---|---|---|---|
| 1 | 钉 `rust-toolchain.toml` + 修 3 处 clippy + 修 `.cargo/config.toml` | 数小时 | 全仓 ROI 最高。没有绿 CI，下面每一件事都无法验证 |
| 2 | 修 §5 的 8 个「严重」缺陷 | 2-3 天 | 全部是用户可见的静默错误（打字错位、卸载失效、传文件必败） |
| 3 | 「换库周」：bindgen / libloading / chrono / hex / uuid / tracing / clap | 1 周 | 替代品已在依赖树，零新增生态成本，可拆 6 个半天 PR |
| 4 | schemas 从硬分叉改为 patch 覆盖层 + 生成物出库 | 1-2 周 | 唯一一条通往「上游还能升级」的路，且有 20 个引擎集成测试做安全网 |
| 5 | 建 `core/ime-policy`，把 IME 策略从 Windows 传输层搬出来 | 2-3 周 | 消灭双端行为分叉的根因 |

## 1. 审查方法与覆盖范围

10 个子系统并行测绘 → 逐子系统细节缺陷审查 → 三种独立视角的架构评审（分层边界 / 生态复用 / 单人可维护性）→ 结论交叉验证。共 38 个审查单元、约 700 万 token、1,700 次工具调用。

**覆盖**：`core/`（5 crate）、`platforms/`（7 crate + Android app）、`schemas/`、`scripts/`、`installer/`、`.github/`、`docs/`。

**关键数字均已独立复核**，包括：亲自跑 `gh run list` 确认 CI 历史、`git log --numstat` 确认删增比、`diff` 确认两份 schema 差异、`stat` 确认生成物体积。

**审查者之间的分歧已保留并裁决**（这是本报告可信度的一部分）：

- 测绘者把 `core/sync` 列为「自研加密协议栈」→ **被推翻**。实读 `core/sync/src/tls.rs:9-15`，签名校验委托给 rustls 的 `verify_tls12_signature`/`verify_tls13_signature`，证书用 rcgen，发现用 mdns-sd，**没有一行手搓密码学**。
- 测绘者把 `schemas/lua/` 列为「自研方案脚本」→ **被推翻**。2,304 行里绝大部分是上游 rime-ice / 社区插件的原样复制且**保留了作者署名**（如 `calc_translator.lua:2-3`）。真正自研的只有 4 个小文件。
- 测绘者称 `core/sync` 只有 6 个测试 → **计数错误**，漏了 `#[tokio::test]`，实际 20 个 in-src + 915 行集成测试。
- 测绘者称四大区「零测试」→ **不准确**。`platforms/windows` 有 72 个、`windows-host` 有 49 个测试，但均为纯谓词单测；真正零测试的是 `windows-installer`（1,340 行，跑在管理员权限下）与 `rimejni`（1,641 行，JNI 边界）。

**未覆盖**：运行期真机验证（本报告全部结论基于静态阅读 + 少量本地实测，实测项已在文中标注）；`dsh-*`、`research_rime` 等 gitignored 目录不属项目代码，未审查。

## 2. 最高层判断

### 2.1 这个项目的真实形态

它不是「一个输入法」，而是**七个独立子系统的集合体**：TSF 前端、算法服务、常驻剪贴板进程、Tauri 控制中心、自研安装器、P2P 同步栈、Android 输入法。每一个单独看都接近能用，合起来的维护面对单人来说已经超载。

三位架构评审的独立打分：**45 / 52 / 52（满分 100）**。三人从完全不同的视角出发，落点一致——**能力没问题，纪律有问题**。

### 2.2 做对了什么（这部分不要动）

这些是真资产，任何改造都不该碰：

1. **算法服务进程剥离**（`platforms/windows-algo/src/main.rs:3-6`）。理由写得清清楚楚：leveldb 的 `LOCK` 只能被一个进程持有，多宿主进程会互抢用户词库锁。边界干净、动机可验证、剥离后 TSF DLL 确实不再链接引擎。**全仓最好的一次架构判断。**
2. **`core/sync` 的加密与发现层**。rustls + rcgen + ring + mdns-sd，与 LocalSend/Syncthing 同款模式。所谓「自研同步协议」实际只剩 `protocol.rs` 的 `Message` 枚举，那是产品语义，本来就没有现成方案，且带 `protocol_version` 与 features 协商的前向兼容设计。
3. **引擎层的回归网**。`core/ime-bridge/tests/` 20 个文件 2,504 行，每一个都是「真实编译雾凇词典 → simulate 键序 → 断言候选文本」的黑盒行为测试，全仓 `#[ignore]` 数为 0。这是 rime-ice 词库与 lua 层唯一的安全网。
4. **`core/options` 的 `modify_at` 跨进程文件锁**（`lib.rs:401-434`）。底层用成熟的 fs4 而非手搓 `LockFileEx`，选型理由写进 `Cargo.toml:13-15`，并有 Barrier + 双线程各翻 16 次的真并发测试。**质量最高的一段代码——问题只是它没被推广到另外 4 个 JSON。**
5. **TSF 协议本体的克制**。只实现三个接口，引用计数交给 windows-rs 的 `#[implement]` 宏托管，没有手搓 `QueryInterface`/`AddRef`。`composition.rs` 42 行。膨胀全部发生在它上面的 UI 层——说明分得清哪里该薄。
6. **少数自研有明确依据，应当保留**：超长组合防护（引用 weasel#649）、引擎忙 try-lock 直通（weasel#1867）、命名管道 SDDL 的完整性标签（`pipe.rs:48-50` 记录了 2026-08-14 提权后 IPC 全拒 err=5 的实机事故）、algo 健康探针、`ffi.rs:372-444` 的 `self_module_dir`（TSF 宿主按自身 exe 目录解析静态导入，必须运行期定向加载，libloading 不提供此能力）。

### 2.3 核心病灶：自研面与测试面几乎完全互补

| 层 | 来源 | 测试 |
|---|---|---|
| librime 引擎语义 | 生态复用 | 2,504 行行为测试 ✅ |
| 同步传输 | 生态复用（rustls/tokio） | 20 in-src + 915 行集成 ✅ |
| TSF 前端 9,825 行 | 自研 | 72 个纯谓词单测，渲染/COM/命中测试零覆盖 ❌ |
| 常驻进程 9,460 行 | 自研 | 49 个纯谓词单测，四套 GDI 面板零覆盖 ❌ |
| 安装器 1,340 行 | 自研（**管理员权限**） | **0** ❌ |
| JNI 层 1,641 行 | 自研（**FFI 边界**） | **0** ❌ |

**结论：重构只在不需要重构的地方是安全的。** 这是本报告所有路线图建议的排序依据——凡是要动没有安全网的代码，第一步都必须是「先删」而不是「先改」，因为删除是唯一不需要安全网就能安全执行的大动作。

## 3. 架构级问题

### A【致命】IME 策略层无处安放，导致双端结构性分叉

`core/ime-ipc` 自述是「IPC 协议与管道收发」（`Cargo.toml:6`），实际持有全部输入法业务策略：

- 全局中英状态机 `GLOBAL_ASCII`（`src/server.rs:16`）
- 打字统计埋点（`src/server.rs:85,124`）
- 超长组合防护 `MAX_COMPOSITION_LEN=64`（`src/lib.rs:171`、`server.rs:96-100`）
- 引擎忙 try-lock 直通（`server.rs:105-116`）
- 候选 MRU 装饰回调 `decorate_process_key`（`server.rs:28`）

而这个 crate 有**无条件**的 `windows` 依赖（`Cargo.toml:16`，不是 `[target.'cfg(windows)']`），只能在 Windows 编译。Android 拿不到，只能在 `rimejni/src/lib.rs:171-215` 重写一份更弱的按键路径。

**代价已经现金化**：`platforms/windows/src/ai_candidates.rs:36-45` 有 `should_skip_ai`（简拼 `lwyg` 场景跳过 AI，提交 `04d83c5` 专门修的），Android 的 `AiCandidateManager.kt:60-76` **完全没有该过滤**。同一个 bug 只修了一端。同类分叉还有：AI 客户端四份实现、计算器两份、皮肤解析两份且语义不同（Kotlin 产 ARGB，Rust 产 BGR COLORREF，且 Android 读不到 v2 新增的 metrics/shadow 段）。

「跨端一套皮肤」目前只是口号。

### B【致命】治理层是装饰性的

- **CI 全红**（实测 `gh run list`：main 近 14 次全 failure）。`windows-build` 死在 clippy 的 `too many arguments (8/7)` ×2 与 `this if has identical blocks`；`android-build` 死在 librime Android 资产 404——`curl` 没带 `-f`，把 GitHub 错误页写进 `rime.7z`，7z 报「cannot open as archive」，报错信息与真实原因完全无关。
- **根因是工具链未钉版**：仓库无 `rust-toolchain.toml`，CI 用 `dtolnay/rust-toolchain@stable` 拉浮动最新版。这是**公平的诊断**——不是作者无视 clippy，是本地 1.97 绿、CI 新版红，而没人在看 CI 信号。
- **`.cargo/config.toml` 已入库**且把 Android linker 写死为作者本机绝对路径（`C:\Users\hkm\AppData\Local\Packages\Claude_...\ndk\28.0.13004108\...`）。任何非本机环境的交叉编译必定失败，`ci.yml:81-84` 设的 `ANDROID_NDK_HOME` 完全不参与——因为 linker 是配置项不是环境变量。
- **Release 里从来没有 APK**（`release.yml:99-108` 的 `continue-on-error` 把它伪装成绿灯）。安卓用户按 `README.md:32` 打开 Releases 页，第一步就无法执行，而维护者看 Actions 全绿。
- **15 份验收报告零机器校验**，签发的是无法复现的结论：v1.0.0 于 2026-08-18 14:04 发布，同一次 push 的 CI 结论是 failure，而 `docs/版本管理.md:17` 明文规定的 1.0 准入门槛正是「CI 全绿」。

### C【高】进程与模块边界按「工具」聚合，不按领域

- **`shurufa-host` 是杂物间**：9,460 行装了 13 个模块、22 个 CLI 子命令、四套手写 GDI 面板（`ai_panel.rs` 1769 + `panel.rs` 1004 + `onscreen_kbd.rs` 861 + `speech.rs` 959 = 4,593 行，占 49%）、词库更新器、同步宿主、supervisor。聚合依据是「需要消息循环 / 需要进程入口」，不是职责。修复漂移已经发生：`send_ctrl_v` 两份已分叉（`ai_panel` 独有 Shift 抬起修复），`make_font` 四份。
- **`core/options` 单文件 1,642 行装 5 个不相关领域**：ImeOptions、打字统计、剪贴板收藏、同步台账、应用直达。其中 favorites 属于 `core/clipboard` 的领域、sync_activity 属于 `core/sync` 的领域。同一套原子 JSON 读写模板被复制粘贴 **4 遍**（`:447/:836/:1077/:1261`），而且 4 份不等价——只有顶层 options 走了跨进程文件锁，另外 3 个文件确实被 host / settings 两个进程并发读写，**跨进程写丢失是必然而非偶然**。
- **跨 crate 源码级注入**：`platforms/windows-host/src/panel.rs:43` 用 `#[path = "../../windows/src/skin.rs"]` 把 1,273 行编译进第二个 crate，依赖图上完全不可见，靠 `skin.rs:59-63` 的注释维护本该由 crate 边界保证的约束。
- **TSF DLL 里塞了 6,800 行 UI + 一整套 ureq+TLS HTTP 栈**（`platforms/windows/Cargo.toml:20`），而这个 DLL 会被注入**每一个宿主进程**。weasel 的 `WeaselServer.exe` 正是为此存在——项目已经有两个常驻进程了，轮子放错了地方。

### D【高】schemas 是 rime-ice 的 70MB 硬分叉，上游不可升级

- `git ls-files schemas/` = 66 文件、70MB，**无 submodule、无 `*.custom.yaml`**（Rime 原生的 patch 机制完全没用上）。
- **仓库不知道自己 fork 的是哪个上游 commit**：`schemas/rime-ice-2026.06.30.json` 声明的 sha256 与实际词典 **3/4 对不上**（base 声明 `5a10ef44…` 实际 `3bbf5982…`，ext 与 8105 同样不符，仅 others 相符）。
- **三份生成物提交入库且未被 gitignore**：`shurufa_t9.dict.yaml` 14.7MB、`jianpin_index.txt` 13.2MB、`rime_ice_nojianpin.schema.yaml`——分别由 `scripts/gen-t9-dict.py`、`gen-jianpin-index.py`、`gen-nojianpin-schema.ps1` 产出。而生成脚本硬编码了本机绝对路径（`gen-t9-dict.py:18` 的 `REPO = 'C:/Users/hkm/Documents/shurufa'`），换台机器就跑不了，**产物事实上不可复现**。
- 这个分叉已经产出一个严重缺陷（见 §5「无简拼方案自定义短语全盘失效」）。

### E【高】产出速度与理解带宽脱节

24 天 59,600 行、48 feat : 1 refactor、删增比 0.186。「删除」这个动作在这个仓库里几乎没发生过——所以四份 IPC 客户端样板、四份帧协议实现、三处开机自启、四份 AI 客户端全都还活着。

近期唯一的 refactor 提交（`29dba02`）内容是**照着搜狗混淆类清单重写 AndroidX Preference**——需求源不换，砍掉的代码会在一个月内原样长回来，而且长成新的形状。

### 4.4 自研合理 —— 保留，但要补文档说明

### 4.5 Android 侧的集中问题

Android 是「标准化 + 生态复用」执行得最差的子系统。不是不会用库，是**系统性地拒绝用库**：

- **`res/layout` 目录不存在**，全部 UI 由命令式代码堆出：106 处 `XxxView(this)` 手工构造、20 处内联 `GradientDrawable()`。工程零 Compose 依赖（`build.gradle.kts:106-113` 只有 core、org.json、material），而 `docs/架构说明.md:31,49,72` 三处承诺 Compose。
- **`SettingControls.kt`「自研 Preference 控件库」**：注释自称借鉴搜狗 38 个类，实际做出 6 个函数，且 `switchRow` 用了**已废弃的 `android.widget.Switch`**——而项目已依赖 material 1.12，有 `MaterialSwitch`。
- **列表全部一次性 `addView` 无回收**（候选/历史/表情，`ShurufaImeService.kt:2971-3066,1616-1652,3937-3963`）→ 应换 RecyclerView。
- **100 张缩略图常驻内存**（`:2857-2870`）：`PreparedHistory` 持有已解码 Bitmap，`list(100)` 全量预解码，260×260×4B×100 ≈ 27MB → 应换 Coil。
- **线程调度混用裸 `thread{}`(4 处) + 单线程 Executor + 两个 Handler**，无结构化并发、无取消 → 应换 kotlinx.coroutines。
- **四套手写 SharedPreferences 序列化**（逗号 / `\t` / `\u0001` 三种分隔符），短语文本含 `\t` 即静默丢数据 → 应换 DataStore + kotlinx.serialization。
- **`org.json:json:20240303` 显式依赖与平台内置重复**（`build.gradle.kts:109`），平台类优先，Maven 版实际不生效。
- **AI 候选整功能是死代码**：key 有三个互不相通的来源（面板读 `BuildConfig`、候选读 SharedPreferences `"ai_api_key"`、Windows 读环境变量），而全仓 grep `"ai_api_key"` **只有一处读、零处写**。

## 6. 改造路线图

排序依据：**先恢复验证能力 → 再修用户可见错误 → 再做零成本替换 → 最后动结构。** 凡是要动没有安全网的代码，第一步都是「删」而不是「改」。

### 阶段 0：恢复反馈回路（数小时，ROI 最高）

1. 新建 `rust-toolchain.toml` 钉死 channel（对应本地 1.97）。
2. 修 3 处 clippy 命中（`too_many_arguments` ×2、`if_same_then_else`）→ `windows-build` 立刻转绿。
3. `.cargo/config.toml` 移出版本控制（改 `.example`），或换 **cargo-ndk**（fcitx5-android / trime 同款做法，自动从 `ANDROID_NDK_HOME` 推导）。
4. `ci.yml:88` 的 curl 加 `-fSL`；Android librime 资产 404 的问题要么自建、要么把 android-build 拆成独立 workflow，不要让它长期污染主 gate 的信号。
5. `ci.yml:53-56` 的构建顺序改成与 `build-installer.ps1` 一致（当前 CI 在 `Shurufa.exe` 生成前就构建安装器，`build.rs` 必然 panic）。

> 没有这一步，后面每一件事都无法验证。

### 阶段 1：修严重缺陷（2-3 天）

S1–S8 全部修掉。其中 S1 的最小修复是**一行**（超时路径 `self.pipe = None`），S7 的最小修复是**重跑一次生成器**。

## 7. 明确不建议做的事

避免过度改造，这几件的收益低于风险：

1. **不要动 `core/sync` 的加密与发现层**。rustls + rcgen + mdns-sd 已经是正解。唯一该改的是把 `protocol.rs` 的帧编解码换成 `LengthDelimitedCodec`（顺在换库周里做），以及删掉 `protocol.rs:295-299` 那个对 TLS 流做单字节 `read_exact`、最坏循环 1600 万次的兼容回退路径。**迁 iroh 是可选项不是必选项**——它能顶掉约 80%，但会破坏线格式且需三端同发，排在阶段 4 之后再评估。
2. **不要重写 3,584 行的设置页 vanilla JS**。收益低于风险，冻结增长即可（`render()` 全量重建已经在打补丁续命，但它还能撑）。
3. **不要动 `schemas/lua/`**。18 个里 12 个是上游复制且署名完整，这块的生态复用是合格的。
4. **不要试图「抽象出一个 GDI 面板基类」**——那是把轮子造得更精致。四套面板应该是删一套、迁三套。
5. **候选窗迁出宿主进程**方向上是对的（weasel 的 `WeaselServer.exe` 就是这么做的，多显示器与 DPI 问题的根也在这里），但它要重做锚点、焦点与合成时序，**风险高于当前收益**。等 `core/ime-policy` 建成、UI 层与协议解耦之后再动，成本会低一个量级。

## 8. 一句话总结

24 天、59,600 行、单人——**自研现在看起来免费，是因为还没到还款日**。

第一次 librime 升级（手抄 98 字段 FFI 无任何 offset 断言）、第一次 rime-ice 升级（70MB 硬分叉且不知道 fork 自哪个 commit）、第一个协作者进场（CI 红着、`.cargo/config.toml` 写死本机路径）时，账单会一次性到期。

上面路线图的真正目的不是「消灭自研」——项目里有六处自研是有据可依、应当保留的。目的是**把还款日之前必然爆炸的那几块提前拆掉**，同时把「生态复用」这条原则从 Markdown 搬进 CI，让它下次能真的拦住人。
