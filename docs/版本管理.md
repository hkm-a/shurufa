# 版本管理

> 配套：[发布流程](发布流程.md)（执行步骤）· [开发计划](开发计划.md)（版本与里程碑映射）
> 制定：2026-08-18 ｜ 状态：生效

## 1. 版本号规则

遵循 [SemVer 2.0.0](https://semver.org/lang/zh-CN/)：

- 格式 `MAJOR.MINOR.PATCH`（如 `0.7.1`）。
- **0.x 阶段约定**：`MINOR` = 一个功能批次（可含多个功能/修复）；`PATCH` = 修复、文档与配置变更。
- 预发布后缀：`0.8.0-rc.1` 等，仅用于发布前验证，正式产物不带后缀。
- **1.0 里程碑门槛**（满足才升 1.0）：
  - Windows TSF 与 Android IME 双端功能对等、连续两轮验收全绿；
  - 设置中心（M9）整合完成；
  - 跨设备同步协议 v3 冻结并向后兼容；
  - 无已知 P0 缺陷，CI 双平台流水线稳定。
- **Android versionCode**：单调递增的非负整数，只在发布时 bump，与版本号一一对应
  （当前映射：`0.7.1 → 29`）。

## 2. 单一事实源（SSOT）

| 事实 | 文件 | 说明 |
|---|---|---|
| 版本号 | `version.json` | `version` + `versionCode`，唯一手改入口 |
| 结构化派生点（写） | `platforms\windows-installer\tauri.conf.json`、`platforms\windows-settings\tauri.conf.json`、`platforms\windows-settings\package.json`、`platforms\windows-installer\ui\*.html`（品牌版本串） | 由 `set-version.ps1` **自动写入** |
| 文本声明点（只校验） | `README.md` 的状态徽章与「当前版本」段 | 由 `set-version.ps1 -Check` **校验**，需人工修订 |
| 构建期直读（不写） | `platforms\android\app\build.gradle.kts` | 构建时直接读 `version.json`（拉而非推），**不经过任何同步** |
| 变更记录 | `CHANGELOG.md` | Keep a Changelog 格式；当前版本必须有条目，由 `check-docs.ps1` 校验 |
| 路线图 | `docs/开发计划.md` | 版本 ↔ 里程碑映射 |

> **`platforms\android\gradle.properties` 不是派生点。** 曾经是，但固定
> `SHURUFA_VERSION_*` 会与 `version.json` 漂移（实际发生过 0.4.0/9 vs 0.4.1/10）。
> 现在 Android 侧由 `build.gradle.kts` 构建期直读 `version.json`，而
> `set-version.ps1 -Check` 会主动拦截该文件里残留的 `SHURUFA_VERSION_*` 并报错。
> 本地试包请用命令行覆盖：`./gradlew assembleDebug -PSHURUFA_VERSION_CODE=99`。

修改版本号必须走：

```powershell
pwsh -NoProfile -File scripts\set-version.ps1 -Version 0.8.0 -VersionCode 30
```

禁止手工改结构化派生点；`set-version.ps1 -Check` 是构建与 CI 的强制 gate。

新增一处「写死版本号的文档」时，在 `set-version.ps1` 的 `$textClaims` 表里加一行即可
纳入校验，无需改动校验逻辑。这条机制的存在理由：README 曾同时出现三个互相矛盾的
版本号（`version.json`=1.8.0、状态徽章=0.8.0、正文=1.7.0）而无人察觉，因为当时的
`-Check` 只覆盖 4 个 JSON 白名单，不含任何文档。

## 3. 版本节奏

- **常规迭代**：每 1–2 周一个 `MINOR`（0.x），对应一个开发计划里程碑切片；
- **修复**：随时发 `PATCH`（如 `0.7.2`），单文件改动、低风险；
- **里程碑映射**（详见 [开发计划](开发计划.md)）：

| 里程碑 | 目标版本 | 主题 |
|---|---|---|
| M7 | 0.8.x | 候选条升级与打字体验收尾 |
| M8 | 0.9.x | 跨设备与个性化深化 |
| M9 | 1.0 | 设置中心与 AI 助手整合 |
| M10+ | 1.1+ | 专业模式、无障碍、生僻字、语音 |
| M-A1 | 1.3.x | 安卓键盘形态与输入效率（高度/反馈/单手/9 键） |
| M-A2 | 1.4.x | 安卓表达与效率工具（常用语/表情面板/时间日期） |
| M-A3 | 1.5.x | 安卓无障碍与生僻字（触觉/笔画/声文互转） |
| M-A4 | 1.6.x | 安卓 AI 助手深化（帮写风格/快查/转写书面语） |
| M-A5 | 1.7.x | 安卓跨端生态与设置（工具栏/设置极简/专业模式） |

> 安卓里程碑细节见 [开发计划-Android](开发计划-Android.md)；PC 侧路线图已全部完成
> （M1–M11，v1.2.0），后续迭代以安卓为主。

- 一个里程碑可跨多个 MINOR；里程碑完成时写验收报告并更新开发计划状态。

## 4. CHANGELOG 规则

- 顶部永远保留 `## [Unreleased]`；日常改动只进 Unreleased。
- 发布时把 Unreleased 内容落成 `## [X.Y.Z] - YYYY-MM-DD` 段，并清空 Unreleased。
- 条目分类：`新增` / `修复` / `变更` / `废弃`；文档类改动单独列 `文档` 小节。
- 每条目带日期与来源（提交/issue/搜狗对照），便于回溯。

## 5. 分支与标签

- `main` 为唯一常驻分支；功能开发走 `feature/<主题>` 分支，合并后删除。
- 发布走 annotated tag：`git tag -a v0.8.0 -m "v0.8.0"`。
- tag 推送触发 `.github\workflows\release.yml`：版本一致性校验 → 双平台构建 → GitHub Release
  （正文自动取自 CHANGELOG 对应段落）。
- 紧急修复：`PATCH` 直接上 main 后补 tag；当前规模不维护长期 release 分支。

## 6. 发布产物

| 平台 | 产物 | 校验 |
|---|---|---|
| Windows | `Shurufa-Setup-<版本>.exe` | 同目录 `.sha256`，正式发布必须签名 |
| Android | `shurufa-<版本>-<code>-debug.apk` | CI 构建 |

## 7. 发布检查单

1. `cargo test --workspace --locked` 全绿；
2. `pwsh scripts\build-installer.ps1 -Sign`（无证书可省）与 `build-android.cmd` 通过；
3. `set-version.ps1 -Check` 通过；
4. CHANGELOG 段落齐备、README 状态徽章同步；
5. 打 tag 推送，确认 release.yml 全绿、Release 正文正确。

具体步骤与回退策略见 [发布流程](发布流程.md)。
