# 文档管理

> 配套：[开发计划](开发计划.md) · [版本管理](版本管理.md) · [迭代方向](迭代方向.md)
> 制定：2026-08-18 ｜ 状态：生效

## 1. 目录结构

| 分类 | 位置 | 现有文档 |
|---|---|---|
| 产品 | docs/ | 架构说明、迭代方向、开发计划 |
| 用户 | docs/ | Windows 安装指南、安卓安装与使用、云词库、自托管中继 |
| 开发 | docs/ | 开发环境、发布流程、版本管理、文档管理、输入卡顿排查、优化灵感库 |
| 验收 | docs/ | M1–M4 验收报告、安卓附件测试、quality/输入法验收规范 |
| 根索引 | 仓库根 | README.md（导航总索引）、CHANGELOG.md（变更记录） |

## 2. 命名规范

- 中文、语义化、无空格与特殊字符（如 `版本管理.md`，不要 `Version Manage.md`）；
- 同主题系列用前缀区分：`M1-验收报告.md`、`M2-验收报告.md`；
- 文档首部必须包含 `> 制定/更新日期` 与 `> 状态` 两行元信息。

## 3. 文档生命周期

| 状态 | 含义 | 处置 |
|---|---|---|
| 草案 | 未评审 | 头部标注"草案"，不对外引用 |
| 生效 | 当前事实 | 纳入 README 导航索引 |
| 废弃 | 已被替代 | 头部加废弃横幅并指向替代文档；保留可追溯，不删除历史 |

更新触发点：

- 功能落地/发布 → 更新 CHANGELOG + 开发计划状态 + 相关验收/指南；
- 架构或协议变更 → 更新架构说明、迭代方向，必要时记录 ADR；
- 版本规则变更 → 版本管理、发布流程同步。

## 4. 单一事实源（SSOT）原则

- 同一信息只维护一处，其余文档引用它：
  - 版本号 → `version.json`。文档正文原则上**不写死**版本号；确需写的（如 README
    状态徽章）必须登记进 `set-version.ps1` 的 `$textClaims` 表，否则会漂移且无人察觉。
  - 变更记录 → `CHANGELOG.md`；
  - 功能是否已落地 → `docs/开发计划.md` 与 `docs/优化灵感库.md` 的状态列；
  - 文档导航 → `README.md`。
- 新文档必须登记进 README 文档导航，否则视为草稿。

## 5. 交叉引用

- 相对路径链接（docs/ 内互相引用直接用文件名）；
- 变更文档时同步检查所有引用它的文档，避免悬空链接；
- 修订计划/版本/方向三者之一时，必须检查另外两份的一致性。

## 6. 变更记录

- 文档类改动进 CHANGELOG `[Unreleased] → 文档` 小节；
- 重大决策（协议、架构、发布策略）评审后在文档头部记录决策日期。

## 7. 新文档检查单

- [ ] 命名符合规范、头部含日期与状态；
- [ ] 内容满足 SSOT（不重复既有事实）；
- [ ] 已登记 README 文档导航；
- [ ] 已在 CHANGELOG Unreleased 记录；
- [ ] 相关文档交叉引用已更新。

## 8. 机器门禁（CI 强制）

第 7 节的检查单是人工的，人工检查单在单人项目里会失效——本仓曾同时存在三个互相
矛盾的「当前版本」、一条指向未入库文件的链接、一处用全角）闭合的坏链接，以及四项
与实现相反的架构承诺，全部通过了上面的检查单。

因此以下三条改为机器执行，写进 CI：

| 规则 | 执行者 |
|---|---|
| 文档内部链接必须可达（含全角括号闭合的坏链接） | `scripts/check-docs.ps1` |
| 文档里写死的「当前版本」必须等于 `version.json` | `scripts/check-docs.ps1` + `set-version.ps1 -Check` |
| CHANGELOG 必须有当前版本的条目 | `scripts/check-docs.ps1` |

**核心原则：写不进 `check-docs.ps1` 的文档承诺，就不要写进文档。**

想新增一条可校验的文档规则，就往 `check-docs.ps1` 加一段检查；如果一条规则无法
被机器验证（例如「本文档描述与实现一致」），那它就只能靠人，而靠人的部分要尽量少、
且必须集中在 [架构说明](架构说明.md) §8.2 要求的决策记录里。

## 9. 验收报告的定位

`M*-验收报告.md` 是**历史快照**，记录某个里程碑当时的验收情况，不代表当前状态。
它们不是活的质量信号——活的质量信号是 CI。

原因：这些报告以「本地实测全绿」形式自证，无法复现也无法证伪。实际情况是
v1.0.0 发布当刻 CI 即为失败状态，而 [版本管理](版本管理.md) §1 明文规定的 1.0
准入门槛正是「CI 双平台流水线稳定」——报告与事实不符却无人发现。

因此：

- 新的验收结论**必须引用 CI run 链接**，不再手抄「全绿」；
- 历史报告保留可追溯（见 §3 生命周期），但头部标注为历史快照；
- 判断「当前是否健康」请看 CI 徽章与 `scripts/` 下的四个门禁脚本。
